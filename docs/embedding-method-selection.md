# 임베딩 모델·추천 방식 선택 근거

크리에이터 소개글로 "비슷한 크리에이터"를 추천할 때 쓸 임베딩 모델과 방식을 100명 합성 데이터로 비교한 결과다. **결론과 용어 정리만 읽어도 흐름을 알 수 있고, 근거는 그 아래 절에 있다.**

## 결론

**세 줄 요약**

1. 임베딩 모델은 **`bge-m3`**, 방식은 **M4 또는 M3**를 1순위 후보로 제안한다. 확정 채택은 아니다.
2. 확정하지 못하는 이유: 태그 보정이 M2(순수 임베딩)보다 관련도를 **0.1 이상** 올려야 채택한다는 사전 기준을 어느 설정도 넘지 못했다. `bge-m3` M4가 +0.094로 가장 근접했다.
3. 대안은 **`KURE-v1` M2**(태그 보정 없이도 견고)와 **`bge-m3` M3**(외부 LLM 불필요, 재현성 좋음)다.

### 한눈에 보기

| 역할 | 결론 | 한 줄 근거 |
| --- | --- | --- |
| 임베딩 모델 | **`bge-m3`** (1순위) | E2 관련도 단독 1위(M4 0.487), 태깅 Top-3 포함률 1.000 |
| 임베딩 모델 (대안) | **`KURE-v1`** | E1 Top-1 1위(0.914), 태그 보정 없는 M2만으로 E3 ①~③ 7/7 |
| 추천 방식 | **M4** 또는 **M3** | M4가 근소 우위지만 LLM 운영 부담과 재현성 문제가 있음 |
| 태깅 LLM (M4용) | `gpt-5.4-nano` | dev 기준 F1 0.900, 후보 `gpt-4.1-nano`(0.833)보다 우세 |
| 판정 LLM (E2용) | `gpt-5.4-mini` | 태깅 모델보다 강한 모델로 자기 채점 편향을 줄임 |
| 채택 안 함 | `Qwen3-Embedding-0.6B`, `text-embedding-3-small`, M5(리랭커) | 아래 "채택하지 않은 이유" |

**무엇을 우선하느냐에 따른 선택**

| 우선하는 것 | 선택 | 감수할 점 |
| --- | --- | --- |
| 관련도 | `bge-m3` + M4 | 운영 중에도 LLM 태깅(비용·지연·장애 대응)을 유지해야 하고, 실행마다 결과가 조금씩 달라짐 |
| 재현성, 외부 LLM 없이 운영 | `bge-m3` + M3 | 관련도가 M4보다 근소하게 낮음(0.447 대 0.487) |
| 가장 단순한 파이프라인 | `KURE-v1` + M2 | 관련도가 더 낮음(0.420), 소개 부족 사례(④)에서 X08·X10 실패 |

### 용어 정리

**추천 방식**

| 기호 | 뜻 |
| --- | --- |
| **M1** | 태깅(zero-shot) 단독. 태그를 붙인 뒤 공유 태그 Jaccard(겹치는 정도)로 비교 |
| **M2** | 임베딩 단독. 소개글 벡터의 코사인 유사도 |
| **M3** | M2 + zero-shot 태그가 겹치면 가산점(bonus). 외부 LLM 불필요 |
| **M4** | M2 + LLM이 붙인 태그가 겹치면 가산점(bonus) |
| **M5** | `bge-m3` M2 상위 20명을 `bge-reranker-v2-m3`로 다시 채점·정렬 |
| **R1·R2** | 참고용. 사람이 입력한 분야를 쓰므로 실제보다 유리한 상한선 |

**평가와 지표**

| 기호 | 뜻 |
| --- | --- |
| **E1** | zero-shot 태깅 정확도. Top-1은 1순위 태그가 정답인 비율, Top-3 포함률은 상위 3개 안에 정답이 있는 비율 |
| **E2** | 추천 관련도. 쿼리 30명의 상위 5명을 LLM이 0/1/2점으로 판정 |
| **E3** | 어려운 대표 사례 통과 여부(아래 사례 표) |
| **E4** | 운영 지표(비용·시간·메모리) |
| nDCG | 순위까지 고려한 관련도(높을수록 좋음) |
| 무관비율 | 상위 5명 중 무관하다고 판정된 비율(낮을수록 좋음) |
| tau | zero-shot 태그를 붙이는 기준값. 모델별로 dev에서 선택 |
| bonus | 태그가 겹칠 때 더하는 가산점. 방식별로 dev에서 선택 |
| 컷오프 | 유사도 점수가 이 값보다 낮은 후보를 추천에서 빼는 기준 |

**E3 대표 사례** (합성 데이터에 일부러 넣은 어려운 크리에이터. 표의 X01·K07 등은 크리에이터 ID)

| 번호 | 무엇을 보나 | 대표 사례 |
| --- | --- | --- |
| ① 동의어 | 단어가 달라도 같은 뜻이면 비슷하다고 보는가 | F01 홈트 ↔ F02 맨몸운동, X12(대식가, "먹방" 단어 없음) ↔ K03 먹방, X13 데일리룩 ↔ S01 |
| ② 경품 잡음 | 소개글의 경품 문구에 끌려 무관한 크리에이터가 추천되지 않는가 | X01 파스타공방("닌텐도 스위치 증정"), X02 스쿼트요정("플스5 추첨") |
| ③ 분야 넘기 | 분야가 달라도 실제로 비슷한 크리에이터를 찾는가 | X14 푸드 여행 → K07 맛집(요리 분야), X15 웨어러블 → F06 |
| ④ 소개 부족 | 정보가 거의 없는 입력에서 엉뚱한 추천을 하지 않는가 | X08("안녕하세요"), X10(이벤트 제목만) |

①~③은 7건, ④는 2건이라 전체 9건이다. ④는 컷오프 실험(이슈 #10)에서 추가됐다.

### 채택하지 않은 이유

| 대상 | 이유 |
| --- | --- |
| `Qwen3-Embedding-0.6B` | 관련도는 높지만(M4 0.473) E1·E3에서 한 단계 약함. 쿼리 프롬프트 재측정 후 E3 M4가 5/7 → 6/7로 올랐지만 X14→K07 "분야 넘기"는 여전히 못 풂 |
| `text-embedding-3-small` | 태깅 Top-1 0.729로 가장 낮고 X14→K07을 못 풂. bge-m3와 관련도 차이가 0.05를 넘어 품질 기준으로 bge-m3 우위 |
| M5 (`bge-m3` M2 + 리랭커) | nDCG는 전체 최고(0.553)지만 경품잡음(X01·X02) 둘 다 실패. **관련도를 높이는 것과 잡음에 강한 것은 다른 문제** |

### M3 vs M4: 재현성

캐시 무효화를 고치면서 LLM 태깅을 두 번 다시 돌렸더니 결과가 달라졌다.

- **M4:** 두 번째 실행에서 `M4_openai`·`M4_qwen3`가 X02 경품잡음에 새로 걸렸다. `M4_bge-m3`만 두 번 다 통과했다. LLM 응답이 실행마다 조금씩 달라져 E3 통과 여부가 흔들린다.
- **M3:** 임베딩만으로 결정돼 `bge-m3`·`KURE-v1`에서 두 번 다 7/7로 안정적이었다.
- **정리:** 관련도만 보면 M4가 근소 우위다. **재현성을 중요하게 본다면 M3가 더 신뢰할 수 있는 선택**이다.

### 운영 조건과 과제 범위

- **서버 메모리:** 모델 하나 기준 CPU에서 약 1.9~2.3GiB, M5(bge-m3 + 리랭커)를 함께 올리면 약 3.8GiB (아래 "로컬 모델 메모리 사용량")
  - 서버에 올리지 않고 같은 bge-m3를 API(DeepInfra)로 써도 **벡터·유사도는 사실상 같다**(유사도 최대 차이 0.0006). 다만 **같은 tau·bonus·컷오프를 그대로 쓰면 경계에 놓인 크리에이터 몇 명의 태그·후보가 달라진다** (아래 "로컬 ↔ API bge-m3 동등성")
- **취향 요약문 → 크리에이터 탐색**(서비스 쿼리 형식이 확정되기 전의 탐색):
  - M4가 로컬 임베딩 3종 모두에서 가장 높았다. M4 > M3 > M2 전체 순위는 bge-m3·KURE-v1만 두 평가에서 같고, Qwen3는 M2·M3 순서가 다르다.
  - Qwen3가 약하지 않았고, bge-m3·KURE-v1 M2 단독은 쿼리가 길어질수록 흔들렸다 (아래 "사용자 취향 쿼리 검증").
  - 형식이 정해지면 다시 확인한다("남은 과제").
- **한계:** 모든 수치는 100명 합성 데이터의 경향이며 실제 운영 규모 재검증 전까지 확정 성능이 아니다.

## E1. zero-shot 태깅 정확도 (test 70명)

> **이 절의 결론:** KURE-v1이 1순위 태그 정확도(Top-1)가 가장 높고, bge-m3·KURE-v1은 상위 3개 안에 정답을 전부 넣는다. OpenAI가 가장 낮다.

| 지표 | text-embedding-3-small | bge-m3 | KURE-v1 | Qwen3-Embedding-0.6B |
| --- | ---: | ---: | ---: | ---: |
| tau | 0.2706 | 0.4801 | 0.4745 | 0.3587 |
| Top-1 정확도 | 0.729 | 0.871 | **0.914** | 0.886 |
| Top-3 포함률 | 0.886 | **1.000** | **1.000** | 0.986 |

- KURE-v1이 네 모델 중 Top-1 정확도가 가장 높다. bge-m3와 같은 베이스를 한국어로 파인튜닝한 효과로 보인다.
- bge-m3·KURE-v1은 test 70명 전원이 상위 3개 안에 정답 분야를 포함했다.

- 쿼리 30명 규모에서는 상위권을 통계적으로 구분하기 어렵다. **E1·E3를 같이 봐야 갈린다.**

### Qwen3 쿼리 프롬프트 재측정 (이슈 #8)

Qwen3-Embedding 모델에 등록된 쿼리용 instruct 프롬프트(`prompt_name="query"`)를 평가 쿼리 30명에 적용해 재측정했다(`src/clients/local_embedding.py`·`_query_prompted_vectors()`).

- **적용 방식:** 프롬프트 벡터는 쿼리 쪽(행)에만 쓰고 후보 쪽(열)은 원래 벡터를 쓴다. 처음 구현은 하나의 배열을 덮어써 쿼리끼리 서로의 후보가 될 때 후보 벡터까지 바뀌는 오류가 있어(리뷰로 발견) 분리한 뒤 다시 측정했다.
- **bonus 선택:** `select-params`가 dev 행에도 쿼리 프롬프트를 적용해 평가와 같은 조건으로 bonus를 고른다(재리뷰로 발견). Qwen3의 bonus 세 개가 모두 0.3에서 0.2로 바뀌었고 다른 모델은 그대로다. 집계 지표는 R2_qwen3만 움직였다.
- **E2 관련도 변화:** 신뢰구간 안에서 방향이 엇갈렸다.

  | 설정 | 변화 |
  | --- | --- |
  | M2_qwen3 | 0.400 → 0.407 |
  | R2_qwen3 | 0.420 → 0.440 |
  | M3_qwen3 | 0.407 → 0.380 |
  | M4_qwen3 | 0.487 → 0.473 |

- **E3 변화:** `M4_qwen3`가 5/7 → 6/7로 올랐다(경품잡음 X02를 더는 놓치지 않음). 이 프롬프트는 집계 지표보다 개별 하드케이스에 더 뚜렷한 영향을 줬다.
- **주의:** 프롬프트 문구가 "웹 검색 질의에 답하는 문서를 찾으라"는 검색 과제용이라, 크리에이터 간 유사도라는 실제 과제와 의미가 정확히 맞지는 않는다. 서비스 쿼리 조건이 정해지면 다시 확인해야 한다.

### 신뢰도 검증 (spot-check)

- **문제와 수정:** 처음 구현한 spot-check는 M4를 baseline들의 합집합과 비교해, "M4=A, M3=B, R2=A"처럼 다른 baseline이 우연히 같은 후보를 가지면 실제 차이를 놓치는 편향이 있었다(리뷰로 발견, 회귀 테스트 추가). M4 vs M3, M4 vs R2를 각각 **양쪽 차집합**으로 직접 비교하도록 고쳤다.
- **효과:** 불일치 쌍이 12쌍에서 **139쌍**으로 늘었다. 처음 버전이 M4 우위의 근거를 실제보다 좁게 보고 있었다는 뜻이다.

### 핵심 발견

**1. 분야 넘기(X14, X15)**
- 입력 분야(declared) 기반 방식(R1, R2)에서만 계속 실패한다. declared 보정은 정의상 분야를 넘는 유사성을 찾지 못하므로 당연한 결과다.
- openai 임베딩은 X14→K07(요리 크리에이터의 유사 목록에 여행 크리에이터가 들어가야 하는 사례)에서 모든 방식이 약했다. bge-m3·KURE-v1(M2 이상)만 이를 풀었다.

**2. 경품 잡음(X01·X02) 테스트는 리뷰 전까지 실제로는 검증되지 않고 있었다**
- `Creator.input_text()`는 `bio`가 있으면 `events`를 아예 안 쓰는데, X01·X02는 경품 문구가 `events`에만 있고 `bio`는 따로 있어서 모델이 경품 문구를 한 번도 본 적이 없었다(리뷰로 발견).
- `bio`에 경품 문구를 직접 넣어 재검증하자 **M2_bge-m3(순수 임베딩)는 X01에서 "닌텐도 스위치" 문구에 끌려 무관한 게임 크리에이터(G09)를 상위 5명에 포함시켜 실패**했다.
- M3·M4(태그 보정 적용)는 여전히 통과했다. 태그 보정이 경품 잡음에 실제로 강하다는 첫 근거다.

**3. KURE-v1은 M2만으로도 ①~③ 7종을 전부 통과한 유일한 설정이다**
- ④ 소개 부족 2사례를 더한 9건에서는 M2_kure-v1이 X08·X10에 실패해 7/9다.
- bge-m3는 M2 단독으로는 X01에 걸려 M3·M4 보정이 필요한 반면, KURE-v1은 보정 없이도 경품 문구에 끌리지 않았다. 운영 비용·지연 관점에서 눈여겨볼 결과다.
- 다만 E2 관련도는 M2_kure-v1(0.420)이 M4_bge-m3(0.487)보다 낮다. "더 견고하지만 관련도는 살짝 아쉬운" 트레이드오프다.

**4. M5(리랭커)는 관련도·nDCG를 올리지만 경품 잡음에는 M2보다 더 취약하다**
- M2 대비 관련도 0.393 → 0.460, nDCG는 전체 최고인 0.553이다.
- M2는 X01만 실패했지만 M5는 X01·X02 둘 다 게임 크리에이터(G05)를 상위 5명에 포함시켰다.
- 태그 보정(M3·M4)은 "태그가 겹치는가"라는 구조화된 신호로 경품 문구 같은 표면적 겹침을 걸러낸다. cross-encoder 리랭커는 두 텍스트를 통째로 비교하기 때문에 경품 문구의 표면적 유사성에 더 크게 반응한 것으로 보인다.
- **관련도를 높이는 것과 잡음에 강한 것은 서로 다른 문제**라는 근거다.

## 선택 이유와 한계

### 선택 이유

수치 근거는 위 E1~E3와 "사전 판단 기준 대비 결과" 표에 있고, 여기서는 후보별 판단만 정리한다.

- **`bge-m3` + M4 (1순위 후보)**
  - E2 관련도 점 추정치가 단독 1위(0.487)다. 다만 Qwen3+M4(0.473)·KURE-v1+M4(0.467)·M5_bge-m3(0.460)와 신뢰구간이 크게 겹친다.
  - 재태깅 재현 실험에서 `M4_bge-m3`만 두 번 다 경품잡음 E3를 통과해, 상위권 중에서는 가장 안정적이었다.
- **`KURE-v1` + M2 (대안)**
  - E1 Top-1 1위(0.914)이고, 태그 보정 없이 E3 ①~③ 7종을 전부 통과했다(④까지 9건으로는 7/9).
  - 보정이 필요 없으니 LLM 의존(비용·지연·장애 대응)이 사라져 파이프라인이 단순해진다. 대신 관련도가 낮다(M2_kure-v1 0.420 대 M4_bge-m3 0.487).
- **`bge-m3` + M3 (대안)**
  - `bge-m3`는 M3·M4가 E3 ①~③에서 동률(7/7)이고(④까지 9건으로는 각각 8/9), E2 차이도 신뢰구간이 겹친다. KURE-v1은 M3 7/7·M4 6/7(9건으로는 둘 다 7/9)이다.
  - M4를 쓰려면 LLM 태깅 파이프라인을 운영 중에도 유지해야 하므로, 이 부담이 크면 M3가 근거 있는 대안이다.
- **M5 (채택 안 함):** 경품잡음 검증에서 M2보다 더 많이 실패했다(2/2 대 1/2). 잡음 필터링을 앞단에 별도로 둔다면 재검토할 만하다(관련도는 태그 보정 없이도 M4에 근접).
- **`Qwen3-Embedding-0.6B` (채택 안 함):** E1 Top-1 0.886, E3에서 M1~M3가 F01↔F02(동의어)를 놓쳤다. 쿼리 프롬프트를 적용해 재측정해도 X14→K07을 못 풀어 bge-m3·KURE-v1에 못 미친다. 서비스 쿼리 형식이 정해지면 그 조건으로 다시 확인해야 한다.

### 사람이 다시 확인한 결과 (타겟 spot-check, 이슈 #8)

**bge-m3 vs KURE-v1**
- 두 모델이 실제로 다르게 추천한 30쌍(M3_bge-m3 vs M2_kure-v1 대칭차집합에서 표본 추출)을 사람이 재판정했다.
- 자동 판정과의 일치율은 높았다. 완전 일치 0.90, ±1 이내 1.00, 2점 차 불일치 없음.
- 의견이 갈린 pick만 보면 bge-m3 쪽이 관련도가 더 높았다. `M3_bge-m3`만 고른 15개의 평균 관련도는 0.33, `M2_kure-v1`만 고른 15개는 0.13이다.
- 표본이 작아(각 15개) 확정적이진 않지만, 전체 E2 집계(M2_kure-v1 0.420 vs M3_bge-m3 0.447)와 같은 방향이다.

**bge-m3+M4 vs Qwen3+M4·M5**
- `M4_bge-m3`가 각각과 실제로 다르게 추천한 쌍(Qwen3 108쌍, M5 142쌍 중)에서 무작위 30쌍씩을 사람이 재판정했다.
- 자동 판정과의 일치율은 완전 일치 0.67(Qwen3)·0.60(M5), ±1 이내 1.00, 2점 차 불일치 없음이다.
- 사람이 자동 판정보다 대체로 후하게 채점하는 경향(불일치 대부분이 사람 1·자동 0)이 있다.
- 의견이 갈린 pick만 보면 두 비교 모두 `M4_bge-m3` 전용 픽이 더 관련도가 높았다.

  | 비교 | 사람 기준 | 자동 판정 기준 |
  | --- | --- | --- |
  | `M4_bge-m3` 전용 vs `M4_qwen3` 전용 | 0.67 대 0.40 | 0.47 대 0.20 |
  | `M4_bge-m3` 전용 vs `M5_bge-m3` 전용 | 0.67 대 0.47 | 0.40 대 0.33 |

- 각 15개 픽이라 확정적이진 않지만, 집계 E2에서 근소하게 앞선 `M4_bge-m3`를 1순위로 두는 판단과 같은 방향이다.

### 한계

- **표본 크기:** 100명(쿼리 30명)은 경향 확인용이며 확정 성능 수치가 아니다.
- **판정 방식:** E2는 사람이 아니라 LLM 자동 판정이다. spot-check로 일부 신뢰도를 확인했다.

  | 비교 | 표본 | 완전 일치 | ±1 이내 |
  | --- | --- | ---: | ---: |
  | bge-m3 내부(M4 vs M3/R2) | 30쌍 | 0.77 | 1.00 |
  | bge-m3 vs KURE-v1 | 30쌍 | 0.90 | 1.00 |
  | `M4_bge-m3` vs `M4_qwen3` | 30쌍 | 0.67 | 1.00 |
  | `M4_bge-m3` vs `M5_bge-m3` | 30쌍 | 0.60 | 1.00 |

  그래도 전체 681쌍을 사람이 본 것은 아니다.
- **판정 독립성:** M4 태깅(`gpt-5.4-nano`)과 E2 판정(`gpt-5.4-mini`)이 같은 회사·계열 모델이라 완전히 독립적인 판정이라고 보기는 어렵다.
- **dev 규모:** dev 30명으로 고른 tau·bonus의 민감도는 합성 300명으로 확인했다(아래 "dev 규모 민감도"). 다만 합성 데이터가 한 LLM이 쓴 균일한 문체라 실제 운영 규모(수백~수천 명)의 다양성까지 검증한 것은 아니다.
- **소개글 작성:** 100명 중 86명은 LLM이 초안을 쓰고 14명만 직접 작성해, 문체가 실제 사용자 입력보다 균일할 수 있다.
- **M5의 구조적 한계:** M2가 이미 추린 상위 20명만 재정렬한다. 리랭커가 M2의 오답(경품잡음으로 끌려온 후보 포함)을 상위권으로 더 끌어올릴 수는 있어도, M2가 애초에 놓친 후보를 새로 찾아오지는 못한다.
- **소개글 결과가 취향 쿼리에 그대로 옮겨지지는 않는다:**
  - 서비스의 쿼리 형식이 아직 정해지지 않아 "취향을 요약한 문장"을 가정해 별도로 확인했다(위 "사용자 취향 쿼리 검증" 절).
  - 방식 순위(M4 > M3 > M2)는 bge-m3·KURE-v1에서만 같았다. Qwen3는 M2·M3 순서가 바뀌고 OpenAI는 M2 > M3이며, 모두 M4가 최상위인 점은 같다.
  - Qwen3는 이 과제에서 약하지 않았고, bge-m3·KURE-v1 M2는 쿼리 표현이 길어질수록 흔들렸다.
  - 그 결과도 합성 쿼리 가정 하의 경향이라, 서비스 쿼리 형식이 확정되면 다시 확인해야 한다.

## dev 규모 민감도 (이슈 #8, `src/pipeline.py dev-sensitivity`)

> **이 절의 결론:** dev를 30명에서 240명까지 늘려도 방식 순위를 뒤집을 만큼 흔들리지 않는다. 즉 dev 30명으로 tau·bonus를 고른 것이 표본 운은 아니었다.

dev 30명으로 tau·bonus를 고른 것이 표본 운에 얼마나 좌우되는지 확인했다.

- **방법:**
  - 후보 풀: 기존 dev 30명 + 합성 300명(`data/creators_large.csv`, gpt-5.4-mini 생성, 카테고리당 30명, 복수 분야·입력분야 오기재·이벤트만 있는 사례 각 30명)
  - 크기 30/60/120/240 부분표본을 각 20번 뽑아 `select-params`와 같은 절차로 tau·bonus를 고른다.
  - 기존 100명에서 gold 기준 대리 지표(태그 F1, 쿼리 30명 P@5)로 평가한다.
- **재현 확인:** 기존 dev 30명 그대로 고른 값이 `selected_params.json`과 4개 모델 모두 일치했다.
- **Qwen3:** `select-params`·평가와 같은 조건으로 dev 행과 test 쿼리 행에 쿼리 프롬프트를 적용해 돌렸다(후보 쪽은 원래 벡터).
- **합성 300명 검증:** 같은 카테고리 안에서 이름·세부주제가 겹치지 않도록 검증한다.

| 모델 | tau 표준편차 (30 → 240) | 태그 F1 평균 (30 → 240) |
| --- | --- | --- |
| text-embedding-3-small | 0.020 → 0.005 | 0.532 → 0.547 |
| bge-m3 | 0.008 → 0.001 | 0.722 → 0.718 |
| kure-v1 | 0.016 → 0.009 | 0.734 → 0.769 |
| qwen3-embedding-0.6b | 0.016 → 0.005 | 0.729 → 0.738 |

- **tau는 dev 30명에서도 이미 안정적이다.** 평균은 크기와 거의 무관(bge-m3 0.496 → 0.496)하고 표준편차만 줄어든다.
- **bonus는 값 자체는 자주 바뀌지만 성능은 거의 그대로다.**
  - 최빈값 비율이 대부분 45~90%이고 0.2·0.3·0.4 같은 이웃 격자값 사이를 오간다.
  - 그러나 test P@5는 거의 그대로다(M3: bge-m3 0.710~0.718, Qwen3 0.625~0.645. M4는 모델별로 크기와 무관하게 사실상 동일).
  - 격자 안의 이웃 값들은 성능 차이가 작아 어느 값을 골라도 결과가 비슷하다.
- **예외: R2(입력분야 태그)는 dev가 커질수록 bonus가 0.1로 내려가고 P@5가 조금 낮아진다.**
  - bge-m3 0.958 → 0.920, KURE-v1 0.959 → 0.900, Qwen3 0.945 → 0.867
  - 합성 데이터에 입력분야 오기재 사례가 10%로 기존 dev보다 많아, 크기가 아니라 **데이터 분포**가 바뀐 효과로 보는 게 맞다.
  - R2는 참고 기준선일 뿐 채택 후보가 아니므로 결론에는 영향이 없다.
- **결론:** 방식 순위를 뒤집을 만큼의 흔들림은 없었다. 다만 합성 데이터가 단일 LLM 생성이라 균일하고, 240명 부분표본은 330명 풀과 겹쳐 분산을 실제보다 작게 본다. test 지표도 LLM 판정 E2가 아닌 gold 기반 대리 지표다.

## 사용자 취향 쿼리 검증 (이슈 #12, `taste-eval`·`taste-judge`)

지금까지의 벤치마크는 "크리에이터 소개글 → 유사 크리에이터"만 검증했다. 서비스의 AI 취향 분석은 사용자의 취향을 요약한 텍스트를 쿼리로 크리에이터를 추천할 가능성이 높아서, 같은 임베딩 모델·방식으로 **취향 요약문 → 크리에이터** 추천도 확인했다.

> **이 절은 형식이 확정되기 전의 탐색 실험이다.** 서비스의 실제 쿼리 형식은 아직 정해지지 않아 "취향을 요약한 문장"을 가정했고, 형식에 민감한지도 함께 봤다.
> 사람 판정이 없고 실제 쿼리 형식으로 검증한 것이 아니므로 선택 근거가 아닌 참고 경향으로만 읽고, 형식이 확정되면 다시 확인한다(이슈 #16).

**실험 설계**
- **쿼리:** `data/taste_queries.csv` 90개(프로필 30개 × 표현 3종).
  - 프로필은 카테고리당 단일 분야 2개와 인접 분야를 함께 좋아하는 1개이다.
  - 표현은 키워드형(쉼표 나열)·문장형(1~2문장)·서술형(3~4문장)이다.
  - gpt-5.4-mini가 카테고리 이름을 그대로 쓰지 않고 구체적 관심사로 표현하게 만들었고, 정답 분야는 코드가 정했다(생성 비용 약 $0.03).
- **방식:** M2(임베딩), M3(쿼리 zero-shot 태그 보정), M4(쿼리 LLM 태그 보정), M5(bge-m3 M2 상위 20을 리랭커로 재정렬). bonus·tau는 기존 `selected_params.json`을 그대로 썼다. Qwen3는 프롬프트 없음, 등록된 기본 쿼리 프롬프트(`prompt-query`), 취향 과제에 맞춰 직접 쓴 instruct 문구(`prompt-taste`) 세 조건을 비교했다.
- **지표:**
  - 정답 분야 기준 P@5(전체 90개)
  - 문장형 30개 × 상위 5 후보 합집합 436쌍을 gpt-5.4-mini가 "이 사용자가 이 크리에이터를 좋아할 가능성"으로 0/1/2 판정한 관련도@5·nDCG@5(판정 비용 약 $0.12). 판정 프롬프트는 이 과제 전용이다.

**결과**
- **방식 순위:** 로컬 임베딩 3종 가운데 bge-m3·KURE-v1은 소개글 → 크리에이터와 같은 M4 > M3 > M2다.
  - Qwen3는 M4가 가장 높은 것은 같지만 M2·M3 순서가 다르다(소개글 평가 M2 0.407 > M3 0.380, 취향 쿼리 M3 1.073 > M2 1.040).
  - OpenAI는 M2(0.880)가 M3(0.860)보다 근소하게 높아 이 순위를 따르지 않는다(신뢰구간 안의 차이).
  - 모든 임베딩에서 M4가 가장 높고 M5는 M4보다 낮다(M5_bge-m3 0.947 대 M4_bge-m3 1.113).
- **Qwen3는 이 과제에서 약하지 않다.**
  - 소개글 → 크리에이터에서는 bge-m3보다 한 단계 아래였지만, 취향 쿼리에서는 M4 기준 Qwen3(1.127~1.153)가 bge-m3(1.113)와 신뢰구간이 크게 겹치는 수준으로 동률이거나 근소하게 높다.
  - M2 단독은 Qwen3 1.033~1.047이 bge-m3 1.000, KURE-v1 0.853, openai 0.880보다 높다.
  - 쿼리(문장)와 크리에이터 소개의 길이·형태가 다른 비대칭 검색에서 쿼리 프롬프트가 있는 모델이 유리한 것으로 보인다.
- **Qwen3 쿼리 프롬프트 문구는 결과를 거의 바꾸지 않는다.**
  - M4 관련도가 프롬프트 없음 1.127, 기본 쿼리 프롬프트 1.153, 취향용 문구 1.127로 차이가 신뢰구간 안이다.
  - 직접 쓴 문구가 기본 프롬프트보다 낫다는 근거는 없다.
  - 이 프롬프트 조건은 selected_params(소개글 → 크리에이터 조건)로 고른 bonus를 그대로 쓴 것이다.
- **쿼리 표현(형식)에 민감한 모델이 있다.**
  - bge-m3 M2는 P@5가 키워드형 0.840에서 서술형 0.680으로, KURE-v1 M2는 0.873에서 0.633으로 떨어진다(긴 서술이 크리에이터 소개 벡터와 덜 맞음).
  - Qwen3 M2(0.827~0.853)와 M4(0.967~0.987)는 표현에 거의 흔들리지 않는다.
  - 서비스 쿼리 형식이 긴 서술형이 되면 bge-m3·KURE-v1 M2 단독은 불리하고, 태그 보정(M3·M4)이 이를 상당 부분 메운다.
- **bge-m3 대 KURE-v1:** 이 과제에서도 차이는 신뢰구간 안이다(M4 1.113 대 1.080, M3 1.047 대 0.913, M2 1.000 대 0.853). 다만 M2·M3에서 bge-m3가 앞서는 폭이 커서, 태그 보정 없이 쓴다면 bge-m3가 더 안전하다.

**한계**
1. 쿼리를 만든 모델(gpt-5.4-mini)과 판정 모델이 같은 계열이라 편향이 있을 수 있다.
2. 문장형 30개만 LLM으로 판정했고 사람 판정은 하지 않았다.
3. 정답 분야 기준 P@5는 태그(분야) 기반 방식에 유리해 M4가 0.94~0.97로 높게 나온다. 방식 간 비교는 LLM 판정 지표를 우선한다.
4. M4는 소개글용 태거로 취향 문장을 분류해서, 취향 요약에 맞춘 프롬프트로 다시 확인하지 않았다.
5. 서비스 쿼리 형식이 확정되면 그 형식으로 다시 확인해야 한다. 이번 결과는 "취향 요약문" 가정 하의 경향이다.

## 로컬 모델 메모리 사용량 (이슈 #13, `python3 -m src.pipeline memory`)

> **이 절의 결론:** 모델 하나는 CPU에서 약 1.9~2.3GiB, bge-m3 + 리랭커(M5)는 약 3.8GiB가 필요하다.

E4 운영 지표에서 빠져 있던 로컬 모델의 메모리를 재서 `results/e4_embedding.json`의 `memory` 항목에 기록했다.

- 최대 상주 메모리(peak RSS)는 줄지 않는 값이라 모델마다 **새 프로세스**에서 하나씩 쟀다(`src/measure_memory.py`).
- 임베딩 3종은 크리에이터 100명 전원을 인코딩하고, 리랭커는 (쿼리, 후보) 100쌍을 채점한 뒤의 값이다.

| 모델 | 기준 (라이브러리만 로드) | 모델 로드 직후 | 100건 처리 후 최대 (CPU) | 이 장비 가속기(MPS)로 처리 후 |
| --- | ---: | ---: | ---: | ---: |
| bge-m3 | 411MiB | 923MiB | **2244MiB** | 930MiB |
| KURE-v1 | 412MiB | 873MiB | **2232MiB** | 962MiB |
| Qwen3-Embedding-0.6B | 411MiB | 572MiB | **1903MiB** | 714MiB |
| bge-reranker-v2-m3 (리랭커만) | 411MiB | 875MiB | **2345MiB** | 982MiB |
| M5 구성: bge-m3 + 리랭커를 한 프로세스에 함께 로드 | 415MiB | 1326MiB | **3904MiB** | 1309MiB |

- **서버 메모리 계획은 CPU 열이 기준이다.** 모델 하나를 CPU로 돌릴 때 최대 약 1.9~2.3GiB이고, 라이브러리(torch 등)만 불러도 약 0.4GiB가 든다. bge-m3와 KURE-v1은 같은 구조라 값이 거의 같고(2.2GiB), Qwen3-Embedding-0.6B가 가장 작다(1.9GiB).
- **M5는 실측값(약 3.8GiB)을 쓴다.** bge-m3와 리랭커를 한 프로세스에 함께 올려 임베딩과 재채점을 모두 처리한 값이다.
  - 따로 잰 두 값의 단순 합(4588MiB)은 공통 런타임과 서로 다른 시점의 최대치를 중복해 세므로 실제보다 크다(기준 411MiB를 한 번만 세도 4177MiB).
  - 모델을 서로 다른 프로세스로 나눠 띄우면 프로세스마다 기준 메모리가 다시 들어간다.
- **가속기(MPS) 열은 서버 근거로 쓰지 않는다.** GPU가 쓰는 메모리는 프로세스 상주 메모리에 잡히지 않아 실제보다 작게 나온다.
- **처리 후 값이 로드 직후보다 큰 이유:** 개별 모델은 1.3GiB 안팎(M5 구성은 두 모델을 함께 처리해 약 2.6GiB) 커진다. 가중치가 처음 쓰일 때 메모리에 올라오고 인코딩 중간 결과가 더해지기 때문이다.
  - 배치 크기(기본 32)와 텍스트 길이에 따라 달라지므로, 실제 서비스에서 긴 텍스트를 한꺼번에 처리하면 더 클 수 있다.
- **측정 조건:** Apple M4 Pro, macOS, torch 2.14.0, 배치 크기 기본값, 크리에이터 소개글 100건(짧은 텍스트). Linux 서버에서는 값이 다를 수 있어 배포 전 같은 명령으로 다시 재는 것이 안전하다.
- **GPU는 필요 없다.** CPU 2스레드(EC2 소형 인스턴스 가정)로 제한해 재면 모델 로드 7.4초, 크리에이터 100명 1.6초(1명당 16ms), 1건 37ms였다(2026-09-29, 같은 장비). EC2 vCPU는 이 장비보다 느려 3~5배로 잡는 것이 안전하지만, 소개글이 바뀔 때만 비동기로 도는 용도에는 충분하다. 로컬 실행의 제약은 속도가 아니라 메모리다.

## 로컬 ↔ API bge-m3 동등성 (이슈 #20, `python3 -m src.pipeline api-parity`)

> **이 절의 결론:** DeepInfra API의 `BAAI/bge-m3`는 로컬 실행과 벡터·유사도가 사실상 같다(유사도 최대 차이 0.0006). 그러나 **같은 tau·bonus·컷오프를 그대로 써도 결과가 완전히 같다고는 말할 수 없다.** 100명 중 태그 2명, 컷오프 뒤 후보 M2 3~4명·M3 5~6명·M4 1명(순위 순서 포함)이 달라졌다. 경계값 근처의 소수 크리에이터 문제이며, API 호출끼리도 서로 다르다.

서버 정밀도(fp16 등) 차이로 벡터가 달라지면 로컬에서 고른 tau·bonus·컷오프가 어긋날 수 있어 두 단계로 비교했다. 로컬 벡터는 `embed` 캐시를 그대로 썼다.

### 1단계. 유사도·이웃 비교 (`similarity_equivalent`)

| 지표 | 결과 | 판정 기준 |
| --- | ---: | ---: |
| 같은 크리에이터의 로컬·API 벡터 코사인 | 최소 0.999998 / 평균 0.999999 | — |
| 크리에이터끼리 유사도 최대 차이 | **0.00042** | 0.01 이하 |
| 크리에이터↔카테고리 유사도 최대 차이 | **0.00042** | 0.01 이하 |
| 상위 5 이웃 겹침 | 평균 **0.996** / 최소 0.8 | 평균 0.95 이상 |
| 1순위 이웃 일치 | **1.000** | — |
| 비용 | 3,404토큰, 약 $0.00003 | — |

- **판정 기준:** 유사도 차이 0.01은 bonus 그리드 간격(0.1)보다 한 자릿수 작게 잡았다(`src/config.py`의 `PARITY_*`). 이 단계는 **유사도가 같은지**만 본다.
- 겹침 최소 0.8은 상위 5명 중 1명만 다른 경우다. 이 표는 가장 최근 `api-parity` 실행 값이며, 호출마다 조금씩 달라진다(1순위 일치는 실행에 따라 0.990~1.000).

### 2단계. 같은 파라미터로 태그·후보 비교 (`parameters_reusable`)

tau는 "점수가 tau 이상이면 태그", 컷오프는 "점수가 컷오프 이상이면 후보 유지"라는 경계 판정이다. 1단계 통과가 이 판정의 동일성을 보장하지 않아, `select-params`가 고른 tau·bonus·컷오프를 로컬·API 벡터에 그대로 적용해 결과를 직접 비교했다(크리에이터 100명, M5 리랭커는 제외). 후보는 **컷오프를 넘은 상위 5명의 순위 순서까지** 같아야 같은 결과로 본다.

| 비교 (달라진 크리에이터 수) | 1회차 | 2회차 |
| --- | ---: | ---: |
| zero-shot 태그 집합 | 2명 (K06, H04) | 2명 (M02, H04) |
| 컷오프 뒤 후보 M1 | 16명 | 10명 |
| 컷오프 뒤 후보 M2 | 3명 | 4명 |
| 컷오프 뒤 후보 M3 | 6명 | 5명 |
| 컷오프 뒤 후보 M4 | 1명 (G01) | 1명 (G01) |

- **1회차와 2회차는 서로 다른 API 호출**이다. 1회차는 임시 스크립트로 저장해 둔 벡터를, 2회차는 `api-parity` 단계의 가장 최근 실행을 순위 순서까지 비교한 값이다. 판정은 두 회차 모두 `parameters_reusable = false`다.
- **순위 순서까지 봐야 불일치가 드러난다.** 후보를 집합으로만 비교하면 1회차에서 M2 1명(K01), M3 2명(N08, P07)의 순서 변화가 숨겨진다(리뷰로 발견).
- **M1의 불일치가 많은 것은 태그 변화의 여파다.** M1은 태그 겹침만으로 유사도를 만들어, 태그가 바뀐 크리에이터와 같은 태그를 가진 크리에이터의 목록이 함께 흔들린다.
- **경계에 놓이는 것은 구조적이다.** `select_tau`와 `select_cutoff`는 둘 다 관측된 점수 값을 경계로 고른다. 그래서 그 점수를 가진 크리에이터가 정확히 경계에 놓인다. 이번 데이터에서 H04의 점수는 tau와 차이가 0.0, K06은 0.000002였다.
- **API 호출끼리도 서로 다르다.** 같은 입력을 두 번 부르면 크리에이터 100명 중 완전히 같은 벡터가 0명이고 유사도 최대 차이가 0.0003이었다(코사인 최소 0.999998). 이 크기는 로컬과 API의 차이(0.0006)와 같은 자릿수라, 불일치 수가 실행마다 달라진다.

### 판단

- **API로 전환해도 되는가:** 유사도와 이웃 순위는 사실상 같아 추천 품질은 유지될 것으로 보인다. 다만 태그·컷오프 경계에 놓인 소수 크리에이터의 결과는 호출마다 바뀔 수 있다는 점을 받아들여야 한다.
- **정확히 같은 결과가 필요하면:** 파라미터를 로컬 벡터가 아닌 API 벡터로 다시 고르는(`select-params`) 방법이 있으나, 경계에 놓인 크리에이터가 API 호출마다 흔들리는 문제는 남는다. 안정적인 경계값(점수 사이의 중간값 등)을 고르는 방식은 이번 범위 밖이다.
- **한계:** 크리에이터 100명, 2회 실행이다. M5(리랭커)와 R2(입력 분야)는 비교하지 않았다. 제공 업체가 서빙 방식을 바꾸면 결과가 달라질 수 있어, 전환 시점에 같은 명령으로 다시 확인하는 것이 안전하다.
- **측정 조건:** 2026-09-29, DeepInfra OpenAI 호환 엔드포인트, 크리에이터 100명 + 카테고리 10개.

## 남은 과제

- **서비스 취향 쿼리 형식 확정 후 재확인 ([#16](https://github.com/URECA-Cking/Cking-LLM-Benchmark/issues/16)):** 위 취향 쿼리 절은 "취향 요약문" 가정 하의 탐색 실험이다. 형식이 정해져야 그 형식으로 다시 확인하고 사람 spot-check까지 할 수 있다.
- **실제 크리에이터 데이터 검증 ([#14](https://github.com/URECA-Cking/Cking-LLM-Benchmark/issues/14)):** 합성 데이터는 문체가 균일하다. 실제 소개글과 정답 분야 라벨이 생기면 순위와 tau·bonus·컷오프가 유지되는지 확인해야 한다.
- 위 두 가지가 정해지기 전까지 이 문서의 결론은 확정 성능이 아니라 100명 합성 데이터의 경향이다.
