# 임베딩 모델·추천 방식 선택 근거

## 결론

**임베딩 모델은 `bge-m3`, 유사도 방식은 M4(임베딩 + LLM 태그 보정) 또는 M3(임베딩 + zero-shot 태그 보정)를 1순위 후보로 제안한다. 다만 이것을 확정 채택으로 발표하지는 않는다.** 4종 임베딩(`text-embedding-3-small`, `bge-m3`, `KURE-v1`, `Qwen3-Embedding-0.6B`) 중 E2 관련도 점 추정치는 `bge-m3`+M4가 0.487로 단독 1위였고(`Qwen3`+M4 0.473, `KURE-v1`+M4 0.467, M5 0.460이 근접), 한국어 특화 임베딩 `KURE-v1`도 강력한 대안이다 — E1 태깅 정확도가 네 임베딩 중 가장 높고(Top-1 0.914), **LLM 태그 보정 없이 순수 임베딩(M2)만으로 E3 ①~③ 7종 사례를 전부 통과**한 유일한 설정이다(④ 소개 부족 2사례까지 9건으로 세면 X08·X10 실패로 7/9이고, 이 기준에서는 `bge-m3` M3·M4가 8/9로 앞선다). (`bge-m3`는 M2 단독으로는 경품잡음에서 실패, M3·M4를 얹어야 통과). `Qwen3-Embedding-0.6B`는 관련도는 높지만(쿼리 프롬프트 적용 재측정 후 M4 기준 0.473) E1·E3에서 `bge-m3`·`KURE-v1`보다 한 단계 약했다 — 공식 권장 쿼리 프롬프트를 적용해 재측정하자 E3에서 M4_qwen3가 5/7→6/7로 올랐지만(아래 한계 참고), 여전히 X14→K07 "분야 넘기" 사례는 못 풀어 최상위권과는 차이가 있다. `bge-m3` M2 후보를 `bge-reranker-v2-m3`로 재정렬하는 M5는 nDCG가 전체 설정 중 가장 높지만(0.553), 경품잡음(X01·X02) 둘 다에 걸려 태그 보정보다 잡음에 약하다 — 관련도를 높이는 것과 잡음에 강한 것은 서로 다른 문제임을 보여준다.

**운영 조건과 과제 범위에 대한 참고**: (1) 서버 메모리는 모델 하나 기준 CPU에서 약 1.9~2.3GiB이고, M5(bge-m3 + 리랭커)는 함께 올리면 약 3.8GiB다(아래 "로컬 모델 메모리 사용량"). (2) 서비스의 취향 요약문 → 크리에이터 추천을 가정한 탐색에서도 M4가 로컬 임베딩 3종 모두에서 가장 높았지만(M4 > M3 > M2 전체 순위는 bge-m3·KURE-v1만 두 평가에서 같고 Qwen3는 M2·M3 순서가 다르다), Qwen3가 약하지 않았고, bge-m3·KURE-v1 M2 단독은 쿼리가 길어질수록 흔들렸다(아래 "사용자 취향 쿼리 검증"). 이 탐색은 서비스 쿼리 형식이 확정되기 전의 것이라 형식이 정해지면 다시 확인한다("남은 과제").

**LLM 재태깅 재현 실험에서 드러난 것**: 캐시 무효화를 재리뷰로 고치면서 LLM 태깅을 두 번 다시 돌렸는데, 두 번째 실행에서는 `M4_openai`·`M4_qwen3`가 X02 경품잡음에 새로 걸렸다(`M4_bge-m3`만 두 번 다 통과). LLM 태그(M4)는 모델 응답이 실행마다 조금씩 달라질 수 있어 E3 통과 여부가 흔들리는 반면, zero-shot 태그(M3)는 임베딩만으로 결정돼 `bge-m3`·`KURE-v1`에서 두 번 다 7/7로 안정적이었다. 관련도만 보면 M4가 근소 우위지만, **재현성을 중요하게 본다면 M3가 더 신뢰할 수 있는 선택**이다. 100명 규모 합성 데이터의 경향 확인이며, 실제 운영 규모 재검증 전까지는 결과를 확정 성능으로 보지 않는다.

**Qwen3 쿼리 프롬프트 재측정**: Qwen3-Embedding 모델에 등록된 쿼리용 instruct 프롬프트(`prompt_name="query"`)를 평가 쿼리 30명에 적용해 재측정했다(이슈 #8, `src/clients/local_embedding.py`·`_query_prompted_vectors()`). 프롬프트 벡터는 쿼리 쪽(행)에만 쓰고 후보 쪽(열)은 원래 벡터를 쓴다 — 처음 구현은 하나의 배열을 덮어써 쿼리끼리 서로의 후보가 될 때 후보 벡터까지 바뀌는 오류가 있어(리뷰로 발견) 분리한 뒤 다시 측정했다. 또한 M3·M4·R2 bonus도 평가와 같은 조건으로 고르도록 `select-params`가 dev 행에도 쿼리 프롬프트를 적용한다(재리뷰로 발견) — 그 결과 Qwen3의 bonus 세 개가 모두 0.3에서 0.2로 바뀌었고(다른 모델은 그대로), 집계 지표는 R2_qwen3만 움직였다. E2 관련도는 M2_qwen3(0.400→0.407)는 소폭 올랐고 R2_qwen3(0.420→0.440)도 올랐고, M3_qwen3(0.407→0.380)·M4_qwen3(0.487→0.473)는 소폭 내려 방향이 엇갈렸다 — 신뢰구간 안에서 유의미한 변화는 아니다. 반면 **E3에서는 `M4_qwen3`가 5/7에서 6/7로 올랐다**(경품잡음 X02를 더는 놓치지 않음, 아래 E3 참고). 즉 이 프롬프트는 집계 지표보다 개별 하드케이스 대응력에 더 뚜렷한 영향을 줬다. 다만 이 프롬프트 문구 자체가 "웹 검색 질의에 답하는 문서를 찾으라"는 검색 과제용이라 크리에이터 간 유사도라는 이 벤치마크의 실제 과제와 의미가 정확히 맞지는 않으므로, 실제 서비스에 쓸 쿼리 조건(사용자 취향 표현 등)이 정해지면 그 조건으로 다시 확인해야 한다.

**신뢰도 검증(spot-check)**: 처음 구현한 spot-check는 M4를 baseline들의 **합집합**과 비교해, "M4=A, M3=B, R2=A"처럼 다른 baseline이 우연히 같은 후보를 가지면 실제 차이를 놓치는 편향이 있었다(리뷰로 발견, 수정 후 회귀 테스트 추가). M4 vs M3, M4 vs R2를 각각 **양쪽 차집합**으로 직접 비교하도록 고치자 불일치 쌍이 12쌍에서 **139쌍**으로 늘었다 — 그만큼 처음 버전이 M4의 우위를 뒷받침하는 근거를 실제보다 좁게 보고 있었다는 뜻이다. 139쌍 전부를 사람이 보기엔 부담이 커서, 고정 시드로 무작위 **30쌍**을 뽑아 사람이 직접 재판정했다. 완전 일치율 0.77, ±1 이내 일치율 1.00으로 극단적 불일치(2점 차)는 없었다.

> LLM 태깅(M4)은 실행마다 결과가 조금씩 달라질 수 있다 — 캐시 무효화 재리뷰로 태깅을 한 번 더 돌리자 `M4_openai`·`M4_qwen3`·`M4_kure-v1`가 새로 X02에 걸렸고, `M4_bge-m3`만 두 번 다 ①~③ 7/7을 유지했다. zero-shot 태깅(M3)은 임베딩만으로 결정돼 `bge-m3`·`KURE-v1`에서 두 번 다 안정적으로 ①~③ 7/7이었다. **이후 Qwen3에 쿼리 프롬프트를 적용해 재측정하자 `M4_qwen3`가 X02를 다시 통과해 6/7로 올랐다** — 위 표는 이 재측정 값이다.

"분야 넘기" 사례(X14, X15)는 입력 분야(declared) 기반 방식(R1, R2)에서만 계속 실패한다. declared 보정은 정의상 분야를 넘는 유사성을 찾지 못하므로 당연한 결과다. openai 임베딩은 X14→K07(요리 크리에이터의 유사 목록에 여행 크리에이터가 들어가야 하는 사례)에서 모든 방식이 약했고, bge-m3·KURE-v1(M2 이상)만 이를 풀었다.

**경품 잡음(X01·X02) 테스트는 리뷰 전까지 실제로는 검증되지 않고 있었다.** `Creator.input_text()`는 `bio`가 있으면 `events`를 아예 안 쓰는데, X01·X02는 경품 문구가 `events`에만 있고 `bio`는 따로 있어서 모델이 경품 문구를 한 번도 본 적이 없었다(리뷰로 발견). `bio`에 경품 문구를 직접 넣어 재검증하자 **M2_bge-m3(순수 임베딩)는 X01에서 "닌텐도 스위치" 문구에 끌려 무관한 게임 크리에이터(G09)를 상위 5명에 포함시켜 실패**했고, M3·M4(태그 보정 적용)는 여전히 통과했다. 태그 보정이 경품 잡음에 실제로 강하다는 것을 보여주는 첫 근거다.

**KURE-v1은 M2(순수 임베딩, 태그 보정 없음)만으로도 ①~③ 7종 사례를 전부 통과한 유일한 설정이다.** (④ 소개 부족 2사례를 더한 9건에서는 M2_kure-v1이 7/9로 X08·X10에 실패한다 — 위 표 참고.) bge-m3는 M2 단독으로는 X01 경품잡음에 걸리고 M3·M4로 태그 보정을 얹어야 통과하는 반면, KURE-v1은 태그 보정 없이도 경품 문구에 끌리지 않았다. LLM 태깅(M4)이나 zero-shot 태깅(M3) 없이도 같은 견고함을 얻을 수 있다는 뜻으로, 운영 비용·지연 관점에서 눈여겨볼 결과다 — 다만 E2 관련도는 M2_kure-v1(0.420)이 M4_bge-m3(0.487)보다 낮아, "더 견고하지만 관련도는 살짝 아쉬운" 트레이드오프다.

**M5(bge-m3 M2 + 재정렬)는 관련도·nDCG를 크게 올리지만(M2 대비 관련도 0.393→0.460, nDCG는 전체 설정 중 최고인 0.553) 경품잡음(X01·X02)에는 M2보다도 더 취약해졌다** — M2는 X01만 실패했지만 M5는 X01·X02 둘 다 게임 크리에이터(G05)를 상위 5명에 포함시켰다. 태그 보정(M3·M4)은 "태그가 겹치는가"라는 구조화된 신호를 더해 경품 문구 같은 표면적 겹침을 걸러내는 반면, cross-encoder 리랭커는 두 텍스트를 통째로 비교하기 때문에 오히려 경품 문구 자체의 표면적 유사성에 더 크게 반응한 것으로 보인다. **관련도를 높이는 것과 잡음에 강한 것은 서로 다른 문제**라는 근거다.

### E3 ④·⑤ 컷오프 적용 (이슈 #10)

- **컷오프 선택**: `select-params`가 dev×dev에서 방식별로 고른다. dev 쿼리의 상위 5 후보 중 정답 분야를 공유하면 남기고 아니면 거르는 정확도가 가장 높은 값이고(동률이면 낮은 값), 점수 >= 컷오프만 남긴다. M5(리랭커)는 점수 척도가 달라 bge-m3 M2 상위 20 후보를 dev×dev에서 리랭커로 다시 채점한 점수로 컷오프를 따로 골랐다.
- **④ 통과 기준**: 컷오프 뒤 남은 후보에 정답 분야가 전혀 다른 크리에이터가 없으면 통과(빈 결과도 통과). 사례는 test 소속인 X08(소개 "안녕하세요"), X10(이벤트 제목만)이다(dev 소속 X09·X11은 컷오프 선택에 관여하므로 제외).
- **⑤ 지표**: 쿼리 30명의 상위 5 후보에서, 정답 분야가 다른 후보 중 컷오프로 제거된 비율(높을수록 좋음), 정답 분야가 같은 후보 중 남은 비율(높을수록 좋음), 컷오프 뒤 후보가 0명인 쿼리 비율.

## 선택 이유와 한계

- **bge-m3 + M4를 1순위 중 하나로 하는 이유**: E2 관련도 점 추정치가 단독 1위(0.487)였고, Qwen3+M4(0.473)·KURE-v1+M4(0.467)·M5_bge-m3(0.460)도 근접해 신뢰구간이 크게 겹친다. 재태깅 재현 실험에서 `M4_bge-m3`만 두 번 다 경품잡음 E3를 통과해, 상위권 중에서는 가장 안정적이었다.
- **KURE-v1을 유력한 대안으로 남기는 이유**: E1 Top-1 정확도가 네 모델 중 가장 높고(0.914), **M2(순수 임베딩, 태그 보정 없음)만으로 E3 ①~③ 7종 사례를 전부 통과한 유일한 설정**이다(④까지 9건으로는 7/9). bge-m3는 M2 단독으로 경품잡음(X01)에 걸려 M3·M4의 태그 보정이 필요했던 반면, KURE-v1은 태그 보정 없이도 견고했다. LLM 태깅·zero-shot 태깅 없이 순수 임베딩만으로 운영할 수 있다면 파이프라인이 단순해지고 M4의 LLM 의존(비용·지연·장애 대응)도 없앨 수 있다 — 대신 관련도는 M2_kure-v1(0.420)이 M4_bge-m3(0.487)보다 낮아, 트레이드오프로 봐야 한다.
- **bge-m3 vs KURE-v1 타겟 spot-check(이슈 #8)**: 두 모델이 실제로 다르게 추천한 30쌍(M3_bge-m3 vs M2_kure-v1 대칭차집합에서 표본 추출)을 사람이 직접 재판정했다. 자동 판정과의 일치율은 높았다(완전 일치 0.90, ±1 이내 1.00, 2점 차 불일치 없음) — 이 30쌍에서의 E2 점수를 신뢰할 근거가 된다. 그리고 **의견이 갈린 pick만 따로 보면 bge-m3 쪽이 더 관련도가 높았다**: `M3_bge-m3`만 고른 15개 픽의 평균 관련도는 0.33, `M2_kure-v1`만 고른 15개 픽은 0.13이었다. 표본이 작아(각 15개) 확정적이진 않지만, 전체 E2 집계(M2_kure-v1 0.420 vs M3_bge-m3 0.447)와 같은 방향이라 bge-m3 우위를 보강하는 근거다.
- **bge-m3+M4 vs Qwen3+M4·M5 타겟 spot-check(이슈 #8)**: `M4_bge-m3`가 각각과 실제로 다르게 추천한 쌍(Qwen3 108쌍, M5 142쌍 중)에서 무작위 30쌍씩을 사람이 재판정했다. 자동 판정과의 일치율은 완전 일치 0.67(Qwen3)·0.60(M5), ±1 이내 1.00, 2점 차 불일치 없음이다. 사람이 자동 판정보다 대체로 후하게 채점하는 경향(불일치 대부분이 사람 1·자동 0)이 있지만, **의견이 갈린 pick만 보면 두 비교 모두 `M4_bge-m3` 전용 픽이 더 관련도가 높았다**: 사람 기준 평균 관련도 `M4_bge-m3` 전용 0.67 대 `M4_qwen3` 전용 0.40, `M4_bge-m3` 전용 0.67 대 `M5_bge-m3` 전용 0.47(자동 판정 기준도 같은 방향: 0.47 대 0.20, 0.40 대 0.33). 각 15개 픽이라 확정적이진 않지만, 집계 E2에서 근소하게 앞선 `M4_bge-m3`를 1순위로 두는 판단과 같은 방향이다.
- **Qwen3-Embedding-0.6B는 이번 데이터에서 한 단계 아래 — 쿼리 프롬프트를 적용해 재측정한 뒤에도 마찬가지다**: E1 Top-1 0.886, E3에서 M1~M3가 F01↔F02(동의어) 사례를 놓쳐 bge-m3·KURE-v1보다 약했다. `LocalEmbeddingClient`가 원래 bge-m3·KURE-v1과 동일하게 접두어 없이 인코딩했는데, Qwen3-Embedding은 모델 자체에 쿼리용 instruct 프롬프트가 등록돼 있고 공식 사용법은 검색 질의 쪽에 이를 적용하길 권장한다는 지적(리뷰로 발견)에 따라 **평가 쿼리 30명에 이 프롬프트를 적용해 재측정했다**(`_query_prompted_vectors()`, 이슈 #8). 결과: E2 관련도는 방향이 엇갈리며 신뢰구간 안에서 변화(M4 기준 0.487→0.473), **E3는 M4_qwen3가 5/7→6/7로 개선**(경품잡음 X02를 더는 놓치지 않음) — 그래도 X14→K07 "분야 넘기"는 여전히 못 풀어 bge-m3·KURE-v1과 동률에는 못 미친다. 이 프롬프트 문구 자체가 "웹 검색 질의에 답하는 문서를 찾으라"는 검색 과제용이라 크리에이터 간 유사도라는 이 벤치마크의 실제 과제와 의미가 정확히 맞지는 않으므로, **실제 서비스에 쓸 쿼리 형식(예: 사용자 취향 요약문)이 정해지면 그 조건으로 다시 확인해야 한다** — 지금 값은 "공식 권장 프롬프트를 그대로 적용"한 조건일 뿐 최종 서비스 조건이 아니다.
- **M3를 M4의 대안으로 남기는 이유**: bge-m3는 M3·M4가 E3 ①~③에서 동률(7/7)이고(④까지 9건으로는 각각 8/9), KURE-v1는 M3 7/7·M4 6/7(9건으로는 M3 7/9·M4 7/9)이며, E2 차이도 신뢰구간이 겹친다. M4를 쓰려면 **운영 중에도 LLM 태깅 파이프라인(비용·지연·장애 대응)을 유지해야 한다** — 이 운영 비용이 부담되면 M3(zero-shot 태그, 외부 LLM 불필요)로도 충분히 근거 있는 대안이다.
- **M5(리랭커)는 채택하지 않는 이유**: nDCG는 전체 설정 중 가장 높지만(0.553), 경품잡음 검증(X01·X02)에서 M2보다도 더 많이 실패했다(2/2 실패, M2는 1/2). 관련도만 보면 매력적이지만 잡음 내성이 약해, 이 벤치마크의 "경품·잡음 문구에 흔들리지 않아야 한다"는 요구를 채우지 못한다. 다만 관련도 자체는 태그 보정 없이도 M4에 근접한 수준까지 올라간다는 점에서, 잡음 필터링을 별도로 앞단에 두는 조건이라면 재검토할 만하다.
- **한계**:
  - 표본 100명(쿼리 30명)은 경향 확인용이며 확정 성능 수치가 아니다.
  - E2는 사람이 아니라 LLM 자동 판정이다. spot-check로 신뢰도를 일부 확인했다 — bge-m3 내부 비교(M4 vs M3/R2, 30쌍) 그리고 bge-m3 vs KURE-v1 비교(30쌍) 둘 다 자동 판정과 높은 일치율(각각 0.77·0.90)을 보였고, `M4_bge-m3` vs `M4_qwen3`·`M5_bge-m3` 비교(각 30쌍)도 완전 일치 0.67·0.60, ±1 이내 1.00이었다. 그래도 전체 681쌍을 사람이 본 것은 아니다.
  - M4 태깅(`gpt-5.4-nano`)과 E2 판정(`gpt-5.4-mini`)이 같은 회사·계열 모델이라, 완전히 독립적인 판정이라고 보기는 어렵다.
  - dev 30명으로 고른 tau·bonus의 민감도는 합성 300명으로 확인했다(아래 "dev 규모 민감도" 절). 다만 합성 데이터가 한 LLM이 쓴 균일한 문체라 실제 운영 규모(수백~수천 명)의 다양성까지 검증한 것은 아니다.
  - 소개글 100명 중 86명은 LLM이 초안을 쓰고 14명만 직접 작성해, 문체가 실제 사용자 입력보다 균일할 수 있다.
  - M5는 M2가 이미 추린 상위 20명만 재정렬한다 — 리랭커가 M2의 오답(경품잡음으로 끌려온 후보 포함)을 상위권으로 더 끌어올릴 수는 있어도, M2가 애초에 놓친 후보를 새로 찾아오지는 못한다.
  - **소개글 → 유사 크리에이터 결과가 취향 쿼리 → 크리에이터에 그대로 옮겨지지는 않는다.** 서비스의 쿼리 형식은 아직 정해지지 않아 "취향을 요약한 문장"을 가정해 별도로 확인했고(위 "사용자 취향 쿼리 검증" 절), 방식 순위(M4 > M3 > M2)는 bge-m3·KURE-v1에서만 같았고(Qwen3는 M2·M3 순서가 바뀌고 OpenAI는 M2 > M3, 모두 M4가 최상위인 점은 같다) Qwen3는 이 과제에서 약하지 않았고 bge-m3·KURE-v1 M2는 쿼리 표현이 길어질수록 흔들렸다. 그 결과도 합성 쿼리 가정 하의 경향이라, 서비스 쿼리 형식이 확정되면 그 형식으로 다시 확인해야 한다.

## dev 규모 민감도 (이슈 #8, `src/pipeline.py dev-sensitivity`)

dev 30명으로 tau·bonus를 고른 것이 표본 운에 얼마나 좌우되는지 확인했다. 기존 dev 30명 + 합성 300명(`data/creators_large.csv`, gpt-5.4-mini 생성, 카테고리당 30명, 복수 분야·입력분야 오기재·이벤트만 있는 사례 각 30명)을 후보 풀로 두고, 크기 30/60/120/240 부분표본을 각 20번 뽑아 `select-params`와 같은 절차로 고른 뒤 기존 100명에서 gold 기준 대리 지표(태그 F1, 쿼리 30명 P@5)로 평가했다. 기존 dev 30명 그대로 고른 값이 `selected_params.json`과 4개 모델 모두 일치함을 확인했다. Qwen3는 `select-params`·평가와 같은 조건으로 dev 행과 test 쿼리 행에 쿼리 프롬프트를 적용해 돌렸다(후보 쪽은 원래 벡터). 합성 300명은 같은 카테고리 안에서 이름·세부주제가 겹치지 않도록 검증한다.

| 모델 | tau 표준편차 (30 → 240) | 태그 F1 평균 (30 → 240) |
| --- | --- | --- |
| text-embedding-3-small | 0.020 → 0.005 | 0.532 → 0.547 |
| bge-m3 | 0.008 → 0.001 | 0.722 → 0.718 |
| kure-v1 | 0.016 → 0.009 | 0.734 → 0.769 |
| qwen3-embedding-0.6b | 0.016 → 0.005 | 0.729 → 0.738 |

- **tau는 dev 30명에서도 이미 안정적이다.** 평균은 크기와 거의 무관(bge-m3 0.496 → 0.496)하고 표준편차만 줄어든다.
- **bonus는 값 자체는 자주 바뀐다.** 최빈값 비율이 대부분 45~90%이고 0.2·0.3·0.4 같은 이웃 격자값 사이를 오간다. 그러나 **test P@5는 거의 그대로**다(M3: bge-m3 0.710~0.718, Qwen3 0.625~0.645. M4는 모델별로 크기와 무관하게 사실상 동일) — 격자 안의 이웃 값들은 성능 차이가 작아 어느 값을 골라도 결과가 비슷하다.
- **예외: R2(입력분야 태그)는 dev가 커질수록 bonus가 0.1로 내려가고 P@5가 조금 낮아진다**(bge-m3 0.958 → 0.920, KURE-v1 0.959 → 0.900, Qwen3 0.945 → 0.867). 합성 데이터에 입력분야 오기재 사례가 10%로 기존 dev보다 많아, 크기가 아니라 **데이터 분포**가 바뀐 효과로 보는 게 맞다. R2는 참고 기준선일 뿐 채택 후보가 아니므로 결론에는 영향이 없다.
- 결론: 방식 순위를 뒤집을 만큼의 흔들림은 없었다. 다만 합성 데이터가 단일 LLM 생성이라 균일하고, 240명 부분표본은 330명 풀과 겹쳐 분산을 실제보다 작게 본다. test 지표도 LLM 판정 E2가 아닌 gold 기반 대리 지표다.

## 사용자 취향 쿼리 검증 (이슈 #12, `taste-eval`·`taste-judge`)

지금까지의 벤치마크는 "크리에이터 소개글 → 유사 크리에이터"만 검증했다. 서비스의 AI 취향 분석은 사용자의 취향을 요약한 텍스트를 쿼리로 크리에이터를 추천할 가능성이 높아서, 같은 임베딩 모델·방식으로 **취향 요약문 → 크리에이터** 추천도 확인했다. 서비스의 실제 쿼리 형식은 아직 정해지지 않아 "취향을 요약한 문장"을 가정했고, 형식에 민감한지도 함께 봤다. **이 절은 형식이 확정되기 전의 탐색 실험이다.** 사람 판정이 없고 실제 쿼리 형식으로 검증한 것이 아니므로 선택 근거가 아닌 참고 경향으로만 읽고, 형식이 확정되면 다시 확인한다(이슈 #16).

- **쿼리**: `data/taste_queries.csv` 90개(프로필 30개 × 표현 3종). 프로필은 카테고리당 단일 분야 2개와 인접 분야를 함께 좋아하는 1개이고, 표현은 키워드형(쉼표 나열)·문장형(1~2문장)·서술형(3~4문장)이다. gpt-5.4-mini가 카테고리 이름을 그대로 쓰지 않고 구체적 관심사로 표현하게 만들었고, 정답 분야는 코드가 정했다(생성 비용 약 $0.03).
- **방식**: M2(임베딩), M3(쿼리 zero-shot 태그 보정), M4(쿼리 LLM 태그 보정), M5(bge-m3 M2 상위 20을 리랭커로 재정렬). bonus·tau는 기존 `selected_params.json`을 그대로 썼다. Qwen3는 프롬프트 없음, 등록된 기본 쿼리 프롬프트(`prompt-query`), 취향 과제에 맞춰 직접 쓴 instruct 문구(`prompt-taste`) 세 조건을 비교했다.

**결과**
- **bge-m3·KURE-v1의 방식 순위는 소개글 → 크리에이터와 같다: M4 > M3 > M2.** Qwen3는 M4가 가장 높은 것은 같지만 M2·M3 순서가 다르다(소개글 평가 M2 0.407 > M3 0.380, 취향 쿼리 M3 1.073 > M2 1.040). OpenAI는 M2(0.880)가 M3(0.860)보다 근소하게 높아 이 순위를 따르지 않는다(신뢰구간 안의 차이). 모든 임베딩에서 M4가 가장 높고 M5는 M4보다 낮다(M5_bge-m3 0.947 대 M4_bge-m3 1.113).
- **Qwen3는 이 과제에서 약하지 않다.** 소개글 → 크리에이터에서는 Qwen3가 bge-m3보다 한 단계 아래였지만, 취향 쿼리에서는 M4 기준 Qwen3(1.127~1.153)가 bge-m3(1.113)와 신뢰구간이 크게 겹치는 수준으로 동률이거나 근소하게 높다. M2 단독은 Qwen3 1.033~1.047이 bge-m3 1.000, KURE-v1 0.853, openai 0.880보다 높다. 쿼리(문장)와 크리에이터 소개의 길이·형태가 다른 비대칭 검색에서 쿼리 프롬프트가 있는 모델이 유리한 것으로 보인다.
- **Qwen3 쿼리 프롬프트 문구는 결과를 거의 바꾸지 않는다.** M4 관련도가 프롬프트 없음 1.127, 기본 쿼리 프롬프트 1.153, 취향용 문구 1.127로 차이가 신뢰구간 안이고, 직접 쓴 문구가 기본 프롬프트보다 낫다는 근거는 없다. 이 프롬프트 조건은 selected_params(소개글 → 크리에이터 조건)로 고른 bonus를 그대로 쓴 것이다.
- **쿼리 표현(형식)에 민감한 모델이 있다.** bge-m3 M2는 P@5가 키워드형 0.840에서 서술형 0.680으로, KURE-v1 M2는 0.873에서 0.633으로 떨어진다(긴 서술이 크리에이터 소개 벡터와 덜 맞음). Qwen3 M2(0.827~0.853)와 M4(0.967~0.987)는 표현에 거의 흔들리지 않는다. 서비스 쿼리 형식이 긴 서술형이 되면 bge-m3·KURE-v1 M2 단독은 불리하고, 태그 보정(M3·M4)이 이를 상당 부분 메운다.
- **bge-m3 대 KURE-v1**: 이 과제에서도 차이는 신뢰구간 안이다(M4 1.113 대 1.080, M3 1.047 대 0.913, M2 1.000 대 0.853). 다만 M2·M3에서 bge-m3가 앞서는 폭이 커서, 태그 보정 없이 쓴다면 bge-m3가 더 안전하다.
- **한계**: (1) 쿼리를 만든 모델(gpt-5.4-mini)과 판정 모델이 같은 계열이라 편향이 있을 수 있다. (2) 문장형 30개만 LLM으로 판정했고 사람 판정은 하지 않았다. (3) 정답 분야 기준 P@5는 태그(분야) 기반 방식에 유리해 M4가 0.94~0.97로 높게 나온다 — 방식 간 비교는 LLM 판정 지표를 우선한다. (4) M4는 소개글용 태거로 취향 문장을 분류해서 취향 요약에 맞춘 프롬프트로 다시 확인하지 않았다. (5) 서비스 쿼리 형식이 확정되면 그 형식으로 다시 확인해야 한다 — 이번 결과는 "취향 요약문" 가정 하의 경향이다.

## 로컬 모델 메모리 사용량 (이슈 #13, `python3 -m src.pipeline memory`)

E4 운영 지표에서 빠져 있던 로컬 모델의 메모리를 재서 `results/e4_embedding.json`의 `memory` 항목에 기록했다. 최대 상주 메모리(peak RSS)는 줄지 않는 값이라, 모델마다 **새 프로세스**에서 하나씩 쟀다(`src/measure_memory.py`). 임베딩 3종은 크리에이터 100명 전원을 인코딩하고, 리랭커는 (쿼리, 후보) 100쌍을 채점한 뒤의 값이다.

| 모델 | 기준 (라이브러리만 로드) | 모델 로드 직후 | 100건 처리 후 최대 (CPU) | 이 장비 가속기(MPS)로 처리 후 |
| --- | ---: | ---: | ---: | ---: |
| bge-m3 | 411MiB | 923MiB | **2244MiB** | 930MiB |
| KURE-v1 | 412MiB | 873MiB | **2232MiB** | 962MiB |
| Qwen3-Embedding-0.6B | 411MiB | 572MiB | **1903MiB** | 714MiB |
| bge-reranker-v2-m3 (리랭커만) | 411MiB | 875MiB | **2345MiB** | 982MiB |
| M5 구성: bge-m3 + 리랭커를 한 프로세스에 함께 로드 | 415MiB | 1326MiB | **3904MiB** | 1309MiB |

- **서버 메모리 계획은 CPU 열이 기준이다.** 모델 하나를 CPU로 돌릴 때 최대 약 1.9~2.3GiB이고, 라이브러리(torch 등)만 불러도 약 0.4GiB가 든다. bge-m3와 KURE-v1은 같은 구조라 값이 거의 같고(2.2GiB), Qwen3-Embedding-0.6B가 가장 작다(1.9GiB).
- **M5는 실측값(약 3.8GiB)을 쓴다.** bge-m3와 리랭커를 한 프로세스에 함께 올려 임베딩과 재채점을 모두 처리한 값이다. 따로 잰 두 값의 단순 합(4588MiB)은 공통 런타임과 서로 다른 시점의 최대치를 중복해 세므로 실제보다 크다(기준 411MiB를 한 번만 세도 4177MiB). 모델을 서로 다른 프로세스로 나눠 띄우면 프로세스마다 기준 메모리가 다시 들어간다.
- **가속기(MPS) 열은 서버 근거로 쓰지 않는다.** GPU가 쓰는 메모리는 프로세스 상주 메모리에 잡히지 않아 실제보다 작게 나온다.
- 개별 모델의 처리 후 값은 로드 직후보다 1.3GiB 안팎 크고(M5 구성은 두 모델을 함께 처리해 약 2.6GiB 크다) — 가중치가 처음 쓰일 때 메모리에 올라오고 인코딩 중간 결과가 더해지기 때문이다. 배치 크기(기본 32)와 텍스트 길이에 따라 달라지므로, 실제 서비스에서 긴 텍스트를 한꺼번에 처리하면 더 클 수 있다.
- 측정 조건: Apple M4 Pro, macOS, torch 2.14.0, 배치 크기 기본값, 크리에이터 소개글 100건(짧은 텍스트). Linux 서버에서는 값이 다를 수 있어 배포 전 같은 명령으로 다시 재는 것이 안전하다.

## 남은 과제

- **서비스 취향 쿼리 형식 확정 후 재확인 ([#16](https://github.com/URECA-Cking/Cking-LLM-Benchmark/issues/16))**: 위 취향 쿼리 절은 "취향 요약문" 가정 하의 탐색 실험이다. 형식이 정해져야 그 형식으로 다시 확인하고 사람 spot-check까지 할 수 있다.
- **실제 크리에이터 데이터 검증 ([#14](https://github.com/URECA-Cking/Cking-LLM-Benchmark/issues/14))**: 합성 데이터는 문체가 균일하다. 실제 소개글과 정답 분야 라벨이 생기면 순위와 tau·bonus·컷오프가 유지되는지 확인해야 한다.
- 위 두 가지가 정해지기 전까지 이 문서의 결론은 확정 성능이 아니라 100명 합성 데이터의 경향이다.
