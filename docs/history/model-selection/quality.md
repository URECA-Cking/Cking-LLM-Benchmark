### 방식 간 차이 (쿼리별 짝 차이)

같은 쿼리 30명에 대해 두 설정의 쿼리별 관련도@5 차이를 구하고, 쿼리를 다시 뽑는(부트스트랩 2,000회) 방식으로 **차이의 평균에 대한 95% 신뢰구간**을 계산했다. 구간이 0을 포함하면 이 표본으로는 차이가 있다고 확인하지 못한 것이다(차이가 없다는 뜻은 아니다).

**재현:** `python3 -m src.pipeline paired-diff`. 입력은 커밋된 `data/e2_judgments.json`(쿼리 30명의 설정별 상위 5 후보와 판정 점수 681쌍, sha256을 `src/config.py`에 고정)이다. 이 파일은 `results/candidates.json`·`results/judge_sheet.csv`(커밋하지 않음)에서 `paired-diff --export`로 만들며, 판정은 `gpt-5.4-mini-2026-03-17` 자동 판정이다(여러 라운드에 걸쳐 누적됐고 라운드별 모델은 기록되지 않았지만, 판정 모델 설정값은 도입 이후 바뀐 적이 없다). 아래 두 표의 모든 행은 테스트가 코드 출력과 행별로 대조한다.

### Qwen3 쿼리 프롬프트 재측정 (이슈 #8)

Qwen3-Embedding 모델에 등록된 쿼리용 instruct 프롬프트(`prompt_name="query"`)를 평가 쿼리 30명에 적용해 재측정했다(`src/clients/local_embedding.py`·`_query_prompted_vectors()`).

- **적용 방식:** 프롬프트 벡터는 쿼리 쪽(행)에만 쓰고 후보 쪽(열)은 원래 벡터를 쓴다. 처음 구현은 하나의 배열을 덮어써 쿼리끼리 서로의 후보가 될 때 후보 벡터까지 바뀌는 오류가 있어(리뷰로 발견) 분리한 뒤 다시 측정했다.
- **bonus 선택:** `select-params`가 dev 행에도 쿼리 프롬프트를 적용해 평가와 같은 조건으로 bonus를 고른다(재리뷰로 발견). Qwen3의 bonus 세 개가 모두 0.3에서 0.2로 바뀌었고 다른 모델은 그대로다. 집계 지표는 R2_qwen3만 움직였다.
- **E2 관련도 변화:** 신뢰구간 안에서 방향이 엇갈렸다.

  | 설정 | 변화 |
  | --- | --- |
  | M2_qwen3 | 0.400 → 0.407 |
  | R2_qwen3 | 0.420 → 0.440 |
  | M3_qwen3 | 0.407 → 0.380 |
  | M4_qwen3 | 0.487 → 0.473 |

- **E3 변화:** `M4_qwen3`가 5/7 → 6/7로 올랐다(경품잡음 X02를 더는 놓치지 않음). 이 프롬프트는 집계 지표보다 개별 하드케이스에 더 뚜렷한 영향을 줬다.
- **주의:** 프롬프트 문구가 "웹 검색 질의에 답하는 문서를 찾으라"는 검색 과제용이라, 크리에이터 간 유사도라는 실제 과제와 의미가 정확히 맞지는 않는다. 서비스 쿼리 조건이 정해지면 다시 확인해야 한다.

### 신뢰도 검증 (spot-check)

- **문제와 수정:** 처음 구현한 spot-check는 M4를 baseline들의 합집합과 비교해, "M4=A, M3=B, R2=A"처럼 다른 baseline이 우연히 같은 후보를 가지면 실제 차이를 놓치는 편향이 있었다(리뷰로 발견, 회귀 테스트 추가). M4 vs M3, M4 vs R2를 각각 **양쪽 차집합**으로 직접 비교하도록 고쳤다.
- **효과:** 불일치 쌍이 12쌍에서 **139쌍**으로 늘었다. 처음 버전이 M4 우위의 근거를 실제보다 좁게 보고 있었다는 뜻이다.
- **표본과 결과:** 139쌍 전부를 사람이 보기엔 부담이 커서 고정 시드로 무작위 **30쌍**을 뽑아 사람이 직접 재판정했다. 완전 일치율 0.77, ±1 이내 일치율 1.00이고 2점 차 불일치는 없었다.

### 핵심 발견

**1. 분야 넘기(X14, X15)**
- 입력 분야(declared) 기반 방식(R1, R2)에서만 계속 실패한다. declared 보정은 정의상 분야를 넘는 유사성을 찾지 못하므로 당연한 결과다.
- openai 임베딩은 X14→K07(요리 크리에이터의 유사 목록에 여행 크리에이터가 들어가야 하는 사례)에서 모든 방식이 약했다. bge-m3·KURE-v1(M2 이상)만 이를 풀었다.

**2. 경품 잡음(X01·X02) 테스트는 리뷰 전까지 실제로는 검증되지 않고 있었다**
- `Creator.input_text()`는 `bio`가 있으면 `events`를 아예 안 쓰는데, X01·X02는 경품 문구가 `events`에만 있고 `bio`는 따로 있어서 모델이 경품 문구를 한 번도 본 적이 없었다(리뷰로 발견).
- `bio`에 경품 문구를 직접 넣어 재검증하자 **M2_bge-m3(순수 임베딩)는 X01에서 "닌텐도 스위치" 문구에 끌려 무관한 게임 크리에이터(G09)를 상위 5명에 포함시켜 실패**했다.
- M3·M4(태그 보정 적용)는 여전히 통과했다. 태그 보정이 경품 잡음에 실제로 강하다는 첫 근거다.

**3. KURE-v1은 M2만으로도 ①~③ 7종을 전부 통과한 유일한 설정이다**
- ④ 소개 부족 2사례를 더한 9건에서는 M2_kure-v1이 X08·X10에 실패해 7/9다.
- bge-m3는 M2 단독으로는 X01에 걸려 M3·M4 보정이 필요한 반면, KURE-v1은 보정 없이도 경품 문구에 끌리지 않았다. 운영 비용·지연 관점에서 눈여겨볼 결과다.
- 다만 E2 관련도는 M2_kure-v1(0.420)이 M4_bge-m3(0.487)보다 낮다. "더 견고하지만 관련도는 살짝 아쉬운" 트레이드오프다.

**4. M5(리랭커)는 관련도·nDCG를 올리지만 경품 잡음에는 M2보다 더 취약하다**
- M2 대비 관련도 0.393 → 0.460, nDCG는 전체 최고인 0.553이다.
- M2는 X01만 실패했지만 M5는 X01·X02 둘 다 게임 크리에이터(G05)를 상위 5명에 포함시켰다.
- 태그 보정(M3·M4)은 "태그가 겹치는가"라는 구조화된 신호로 경품 문구 같은 표면적 겹침을 걸러낸다. cross-encoder 리랭커는 두 텍스트를 통째로 비교하기 때문에 경품 문구의 표면적 유사성에 더 크게 반응한 것으로 보인다.
- **관련도를 높이는 것과 잡음에 강한 것은 서로 다른 문제**라는 근거다.

### E3 ④·⑤ 컷오프 적용 (이슈 #10)

> **이 절의 결론:** 컷오프는 무관한 추천을 거르는 대신 관련 있는 추천도 잃는다. 그래서 컷오프를 쓴다면 서비스가 허용할 무관 추천 비율로 다시 정해야 한다.

계획서의 E3 ④(소개가 한 줄이거나 없는 크리에이터)·⑤(무관한 쌍이 컷오프로 걸러지는가)와 E2 지표 "컷오프 후 빈 결과 비율"을 추가했다. 지금까지 파이프라인에는 컷오프가 없어 top-5를 항상 채웠다.

- **컷오프 선택:** `select-params`가 dev×dev에서 방식별로 고른다.
  - 기준: dev 쿼리의 상위 5 후보 중 정답 분야를 공유하면 남기고 아니면 거르는 정확도가 가장 높은 값(동률이면 낮은 값). 점수 >= 컷오프만 남긴다.
  - M5(리랭커)는 점수 척도가 달라, bge-m3 M2 상위 20 후보를 dev×dev에서 리랭커로 다시 채점한 점수로 컷오프를 따로 골랐다.
- **④ 통과 기준:** 컷오프 뒤 남은 후보에 정답 분야가 전혀 다른 크리에이터가 없으면 통과(빈 결과도 통과). 사례는 test 소속인 X08(소개 "안녕하세요"), X10(이벤트 제목만)이다. dev 소속 X09·X11은 컷오프 선택에 관여하므로 제외한다.
- **⑤ 지표:** 쿼리 30명의 상위 5 후보에서, 정답 분야가 다른 후보 중 컷오프로 제거된 비율(높을수록 좋음), 정답 분야가 같은 후보 중 남은 비율(높을수록 좋음), 컷오프 뒤 후보가 0명인 쿼리 비율.
