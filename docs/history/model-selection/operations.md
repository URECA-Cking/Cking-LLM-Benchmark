## 로컬 ↔ API bge-m3 동등성 (이슈 #20·#22, `python3 -m src.pipeline api-parity`, `api-select-params`)

> **이 절의 결론:** 서버는 API bge-m3로 진행한다. DeepInfra API의 `BAAI/bge-m3`는 로컬 실행과 벡터·유사도가 사실상 같다(유사도 최대 차이 0.0004~0.0006). 그러나 **로컬에서 고른 tau·bonus·컷오프를 그대로 써도 결과가 완전히 같다고는 말할 수 없어**, API 벡터로 파라미터를 다시 골랐다(아래 "결정"). 100명 중 태그 2명, 컷오프 뒤 후보 M2 3~4명·M3 5~6명·M4 1명(순위 순서 포함)이 달라졌다. 경계값 근처의 소수 크리에이터 문제이며, API 호출끼리도 서로 다르다.

서버 정밀도(fp16 등) 차이로 벡터가 달라지면 로컬에서 고른 tau·bonus·컷오프가 어긋날 수 있어 두 단계로 비교했다. 로컬 벡터는 `embed` 캐시를 그대로 썼다.

### 1단계. 유사도·이웃 비교 (`similarity_equivalent`)

| 지표 | 결과 | 판정 기준 |
| --- | ---: | ---: |
| 같은 크리에이터의 로컬·API 벡터 코사인 | 최소 0.999998 / 평균 0.999999 | — |
| 크리에이터끼리 유사도 최대 차이 | **0.00042** | 0.01 이하 |
| 크리에이터↔카테고리 유사도 최대 차이 | **0.00042** | 0.01 이하 |
| 상위 5 이웃 겹침 | 평균 **0.996** / 최소 0.8 | 평균 0.95 이상 |
| 1순위 이웃 일치 | **1.000** | — |
| 비용 | 3,404토큰, 약 $0.00003 | — |

- **판정 기준:** 유사도 차이 0.01은 bonus 그리드 간격(0.1)보다 한 자릿수 작게 잡았다(`src/config.py`의 `PARITY_*`). 이 단계는 **유사도가 같은지**만 본다.
- 겹침 최소 0.8은 상위 5명 중 1명만 다른 경우다. 이 표는 가장 최근 `api-parity` 실행 값이며, 호출마다 조금씩 달라진다(1순위 일치는 실행에 따라 0.990~1.000).

### 2단계. 같은 파라미터로 태그·후보 비교 (`parameters_reusable`)

tau는 "점수가 tau 이상이면 태그", 컷오프는 "점수가 컷오프 이상이면 후보 유지"라는 경계 판정이다. 1단계 통과가 이 판정의 동일성을 보장하지 않아, `select-params`가 고른 tau·bonus·컷오프를 로컬·API 벡터에 그대로 적용해 결과를 직접 비교했다(크리에이터 100명, M5 리랭커는 제외). 후보는 **컷오프를 넘은 상위 5명의 순위 순서까지** 같아야 같은 결과로 본다.

| 비교 (달라진 크리에이터 수) | 1회차 | 2회차 |
| --- | ---: | ---: |
| zero-shot 태그 집합 | 2명 (K06, H04) | 2명 (M02, H04) |
| 컷오프 뒤 후보 M1 | 16명 | 10명 |
| 컷오프 뒤 후보 M2 | 3명 | 4명 |
| 컷오프 뒤 후보 M3 | 6명 | 5명 |
| 컷오프 뒤 후보 M4 | 1명 (G01) | 1명 (G01) |

- **1회차와 2회차는 서로 다른 API 호출**이다. 1회차는 임시 스크립트로 저장해 둔 벡터를, 2회차는 `api-parity` 단계의 가장 최근 실행을 순위 순서까지 비교한 값이다. 판정은 두 회차 모두 `parameters_reusable = false`다.
- **순위 순서까지 봐야 불일치가 드러난다.** 후보를 집합으로만 비교하면 1회차에서 M2 1명(K01), M3 2명(N08, P07)의 순서 변화가 숨겨진다(리뷰로 발견).
- **M1의 불일치가 많은 것은 태그 변화의 여파다.** M1은 태그 겹침만으로 유사도를 만들어, 태그가 바뀐 크리에이터와 같은 태그를 가진 크리에이터의 목록이 함께 흔들린다.
- **경계에 놓이는 것은 구조적이다.** `select_tau`와 `select_cutoff`는 둘 다 관측된 점수 값을 경계로 고른다. 그래서 그 점수를 가진 크리에이터가 정확히 경계에 놓인다. 이번 데이터에서 H04의 점수는 tau와 차이가 0.0, K06은 0.000002였다.
- **API 호출끼리도 서로 다르다.** 같은 입력을 두 번 부르면 크리에이터 100명 중 완전히 같은 벡터가 0명이고 유사도 최대 차이가 0.0003이었다(코사인 최소 0.999998). 이 크기는 로컬과 API의 차이(0.0004~0.0006)와 같은 자릿수라, 불일치 수가 실행마다 달라진다.

### 결정: 서버는 API bge-m3로 진행한다

서버에 로컬 모델을 올리지 않고 DeepInfra `BAAI/bge-m3` API를 쓴다. 모델은 같은 bge-m3이고 서버 메모리 약 2.2GiB가 필요 없어진다. 대신 아래 조건을 전제로 한다.

1. **임베딩은 한 번 계산해 저장하고, 조회·태깅에는 저장한 값을 쓴다.** 같은 입력도 API 호출마다 벡터가 조금씩 달라(완전히 같은 벡터 0/100) 매번 다시 호출하면 경계값 근처 크리에이터의 결과가 흔들린다. 소개글이 바뀔 때만 다시 계산한다.
2. **tau·bonus·컷오프는 API 벡터로 고른 값을 쓴다** (`python3 -m src.pipeline api-select-params`). 이 단계는 처음 받은 API 벡터를 캐시해 같은 입력에서 같은 값이 나오게 하고, `results/selected_params.json`(로컬 기준)은 건드리지 않는다.
3. **업체나 모델이 바뀌면 `api-parity`와 `api-select-params --force`를 다시 실행한다.** 제공 업체가 서빙 방식을 바꾸거나 모델을 교체할 때 해당한다. `api-select-params`는 입력 텍스트와 모델명이 같으면 캐시한 벡터를 그대로 써서, `--force` 없이는 업체가 서빙 방식을 바꿨어도 API를 다시 부르지 않는다.
4. **크리에이터 소개글이 외부 업체(DeepInfra)로 전송된다.** 개인정보·약관 검토는 이 실험의 범위 밖이며 전환 전에 따로 확인해야 한다.

**API 벡터로 다시 고른 파라미터** (dev 30명, 이 실행의 API 벡터를 캐시해 고정)

| 항목 | 로컬 | API | 차이 |
| --- | ---: | ---: | ---: |
| tau | 0.480123 | 0.480022 | 0.000101 |
| bonus M3 / M4 / R2 | 0.1 / 0.2 / 0.2 | 0.1 / 0.2 / 0.2 | 0 |
| 컷오프 M1 | 0.500000 | 0.500000 | 0 |
| 컷오프 M2 | 0.505849 | 0.505831 | 0.000018 |
| 컷오프 M3 | 0.597250 | 0.597238 | 0.000012 |
| 컷오프 M4 / R2 | 0.577308 | 0.577298 | 0.000010 |

- **재선택해도 값은 거의 같다.** bonus는 모두 같고 tau·컷오프는 소수 넷째~여섯째 자리에서 달라진다. 컷오프 M5(리랭커)는 API 벡터 경로에 리랭커가 없어 다시 고르지 않았다.
- **test zero-shot 태깅 정확도는 같다.** Top-1 0.871, Top-3 1.000이 로컬·API 모두 같다.
- **각자 고른 파라미터로 비교하면 불일치가 줄어든다.** 로컬(로컬 파라미터·로컬 벡터)과 API(API 파라미터·API 벡터)를 비교하면 태그가 달라진 크리에이터가 0명이고, 컷오프 뒤 후보가 달라진 크리에이터는 M1 0명, M2 2명(F05, S04), M3 1명(F05), M4 2명(G01, G03)이다. 같은 파라미터를 그대로 쓸 때(태그 2명, M2 3~4명, M3 5~6명)보다 줄지만 0은 아니다.
- **서비스가 API 벡터만 쓴다면 로컬과 같은 결과일 필요는 없다.** 위 불일치는 "로컬과 비교했을 때"의 차이이고, 서비스는 저장한 API 벡터와 API 기준 파라미터를 일관되게 쓰면 된다.
- **한계:** 크리에이터 100명(dev 30), API 벡터 1회분 기준이다. 다른 호출로 받은 벡터에서는 값이 미세하게 달라질 수 있어, 저장한 벡터로 고정하는 것이 전제다. M5(리랭커)와 R2 결과는 비교하지 않았다.
- **측정 조건:** 2026-09-29, DeepInfra OpenAI 호환 엔드포인트, 크리에이터 100명 + 카테고리 10개.

## 남은 과제

- **서비스 취향 쿼리 형식 확정 후 재확인 ([#16](https://github.com/URECA-Cking/Cking-LLM-Benchmark/issues/16)):** 위 취향 쿼리 절은 "취향 요약문" 가정 하의 탐색 실험이다. 형식이 정해져야 그 형식으로 다시 확인하고 사람 spot-check까지 할 수 있다.
- **실제 크리에이터 데이터 검증 ([#14](https://github.com/URECA-Cking/Cking-LLM-Benchmark/issues/14)):** 합성 데이터는 문체가 균일하다. 실제 소개글과 정답 분야 라벨이 생기면 순위와 tau·bonus·컷오프가 유지되는지 확인해야 한다. 실행 도구, 사전 판정 기준, 실행 결과는 [`real-data-eval.md`](../../experiments/real-data/report.md)(이슈 [#28](https://github.com/URECA-Cking/Cking-LLM-Benchmark/issues/28))에 있다. 요약: 실데이터 4,743채널에서 사전 기준의 공식 결과는 M3(M4 − M3 = +0.041, 기준 미달)이지만, 사후 분석(gpt-5.5 재판정 +0.063, 사람 채점 150쌍으로 보정 +0.074)은 M4를 가리킨다. 정답 라벨을 정리해 다시 돌린 v4에서도 공식 판정 +0.053, 사람 채점 보정 +0.071로 M4 방향이다. 다만 사람과 판정기의 일치율이 0.75(v4에서 0.77)로 사전 게이트(0.80)에 못 미쳐 확정하지 않았고(잠정 권고: M4, 공식 결과는 v2의 M3), zero-shot 태그 보정(M3)은 임베딩 단독(M2)보다 거의 낫지 않았다.
- 위 두 가지가 정해지기 전까지 이 문서의 결론은 확정 성능이 아니라 100명 합성 데이터의 경향이다.

- **2026-09-29 (3차) 캐시 저장 보강:** `--force` 갱신이 도중에 실패해도 서로 다른 실행의 벡터·LLM 태그가 유효한 캐시로 남지 않도록 `embed`·`tag-llm`의 저장 순서를 고치고, 후속 단계(`select-params` 등)가 저장이 끝난 캐시(입력 해시가 맞는 것)만 읽게 했다(이슈 #24). 실험 결과와 결론에는 영향이 없다.
